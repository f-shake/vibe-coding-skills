# 阶段五 · 最终验证（可选）

**目标**：在比开发环境更真实的条件上，确认功能真的成立。
**入口**：G5 通过，**或 G3 后用户要求跳过阶段四**。**出口**：本轮选定的验证方式全部通过（G6）。

**进阶段的第一件事是 §1.1**——用户没明确说要测什么，就先停下来问他要跑哪几种。**没问清楚之前，什么验证都不许开跑。**

> 📌 本阶段**每一次回复**的末尾都要带阶段脚注（格式与措辞见 `SKILL.md` §0.1）。问用户选方式那一轮是「继续本阶段 —— 等你选定要跑哪几种」。

> ⚠️ **本阶段可选。** 用户可以在 G3 或 G5 之后直接要求提交、整段跳过——走那条路时**必须在提交信息里注明跳过了什么**（见 `phase-6-commit.md`）。
>
> 原先的环节 ⑫「发布测试」与 ⑬「单元测试」，现已合并为「最终验证」下的**三种可选方式**。

---

## 1. 三种方式，任选——**但选的人是用户，不是你**

| 模式 | 做什么 | 什么时候选它 |
|---|---|---|
| **A · 全量单元测试** | 完整跑一次整个测试套件 | 改动是纯逻辑：核心算法、数据变换、状态机 |
| **B · 端到端接口验证** | **启动服务**，逐个真实调用**本次改动涉及的接口** | 改动带对外入口：HTTP / RPC / CLI |
| **C · 发布测试** | 构建出产物，**调用发布版本**，检查产物是否正确 | 动了构建/打包/依赖，或要确认「发出去还对不对」 |

**挑选原则：改了什么就验什么。** 改接口 → B；动构建配置 → C；改纯逻辑 → A。**可以多选。**

---

## 1.1 进本阶段先做这一件事：问用户要测什么

**判据只有一条：用户在进入本阶段时，有没有明确说要跑哪种方式。**

| 情况 | 你该做什么 |
|---|---|
| 用户**明确说了**（「跑全量单测」「验一下接口」「构建一下试试」） | 按他说的执行。他说的方式覆盖不了本次改动范围时，**提醒一次**，再由他定 |
| 用户**没说**（只说「继续」「确认」，或直接从 G5 过来） | **停下来问**——把 A / B / C 摆出来让他选，**等选完再动手** |

**「没说」是常态，必须主动问，不能默认。**

### 怎么问

**优先用平台的选项式提问工具**（Claude Code 是 `AskUserQuestion`，**多选**）：把 A / B / C 三个选项连同「改了什么就验什么」的**推荐**一起摆出来。平台没有这类工具时，用下面的文字问法，照抄：

> 本次改动是 <一句话摘要：改了哪些文件、有没有动对外接口 / 构建配置>。
> 进入最终验证前，请选本轮要跑哪几种方式（可多选）：
>
> - **A · 全量单元测试** —— 完整跑一遍测试套件。改动是纯逻辑（算法 / 数据变换 / 状态机）时选它。
> - **B · 端到端接口验证** —— 启动服务、真实调用本次改动涉及的接口。改动带对外入口（HTTP / RPC / CLI）时选它。
> - **C · 发布测试** —— 构建产物并在发布版本上验证。动了构建 / 打包 / 依赖时选它。
>
> **我的推荐：<按「改了什么就验什么」给，例如「本次改了 3 个 HTTP 接口 → 推荐 A + B」，并说明理由>**

### 禁止

- **自己选定一种就跑**，或只挑最省事的那种（纯逻辑改动只跑 B、带接口的改动只跑 A，都算选错）。
- **默认「大概率是 A」先跑着等用户回**——那是越权信号，和「先做着等你回」是同一件事。
- **在选项里替用户列出「跳过本阶段」。** 跳过只能由用户自己提（`SKILL.md` §4），你把它摆进选项就是在建议跳过。用户回「跳过」再照跳过规则办。
- 推荐完不等回答就往下走。**推荐只是推荐**——说完就停，等人选。

## 2. 模式 A · 全量单元测试

**跑全量前必须先获批**（见 `SKILL.md` §1 禁令 ③）——整套测试属于需授权动作，**跑单个测试文件/单条用例不受此限**。拿到许可后完整跑一次，确认三项：

| # | 项 | 判据 |
|---|---|---|
| 1 | **新增测试全部通过** | 阶段二写的测试，一条不落 |
| 2 | **原有测试没有被破坏** | 全量跑，不是只跑新增的 |
| 3 | **核心功能没有回归问题** | 关键路径的测试都在并全绿 |

### 「原有测试被破坏」的判定流程

**不要一看到红就直接改测试**——先分辨是哪种。判断依据：回到阶段一的**计划**，看这个行为是否在修改范围内。

```
原有测试失败
  ├─ 断言的是**旧行为**，而旧行为正是本次要改的（在计划范围内）
  │   → 测试过时，**更新测试**，并在提交信息里说明
  └─ 断言的是**仍然成立的行为**（不在计划范围内）
      → **代码真错**，回阶段二修复代码，测试不动
```

禁止为了让测试变绿而直接改断言——那是掩盖回归。

## 3. 模式 B · 端到端接口验证

**由 AI 自己启动服务，逐个真实调用本次修改涉及的接口。**

1. **启动服务**，记录启动命令与端口（写进 G6 报告）
2. **列出本次改动涉及的每个接口**——从阶段一的计划 + 阶段二的实际 diff 取，**不要只挑好调的**
3. **逐个真实调用**（curl / CLI / HTTP 客户端 / 项目自带脚本）。**不用模拟，不走单元测试的桩**
4. 每个接口至少覆盖三类入参：**正常**、**非法**（缺字段 / 类型错 / 越权）、**边界**（空 / 零 / 超长 / 重复）
5. **逐条记录实际响应**，与预期对照

| 接口 | 入参 | 预期 | 实际响应 | 判定 |
|---|---|---|---|---|
| `POST /x` | `{...}` | 200 + `{...}` | `...` | ✅ / ❌ |

**不许只报「服务起来了」。** 起得来 ≠ 功能对——没有逐接口的实际响应记录，本模式不算跑过。

**服务起不来**：先分辨是哪一类。**环境问题**（依赖没装、端口被占、缺环境变量）→ 修环境，**不算测试失败**；**代码问题**（启动即崩、路由没注册）→ 测试失败，按 §5 回退。

## 4. 模式 C · 发布测试

**在发布后的产物上验证**，不是本地本地开发服务器。

| # | 项 | 通过判据 |
|---|---|---|
| 1 | **构建** | 构建成功，无错误；警告逐条判断是否需处理 |
| 2 | **产物完整性** | 产物生成完整，版本号正确，无缺失资源 |
| 3 | **运行环境** | 依赖版本、环境变量、配置项齐备；无「本地有、线上没有」的变量 |
| 4 | **部署**（本项目若无可标「不适用」） | 部署成功，目标环境可达 |
| 5 | **调用发布版本** | 在**发布后的产物**上跑一遍验收用例：核心功能正常，与阶段四验收结果一致 |

**第 5 项是重点**：阶段四验的是「对不对」，这里验的是「**发出去还对不对**」。

### 环境差异排查清单

本地过、发布后不过时，按顺序排查：

- 环境变量 / 配置项缺失
- 构建时的 tree-shaking 或压缩破坏了副作用
- 依赖版本在 CI 中不同（lockfile 未提交）
- 大小写敏感（Windows 开发 → Linux 部署）
- 相对路径 / 资源路径在子目录部署下失效
- 缓存（CDN / 浏览器 / 构建缓存）返回旧版本
- 生产模式下的严格检查（Vue 的生产模式、React 的 StrictMode、TS 严格性）

---

## 5. 失败回流

| 失败性质 | 回流到 |
|---|---|
| 测试过时（断言的是本次要改的旧行为） | 更新测试，**不算失败** |
| 代码真错 | 阶段二修复 |
| 暴露设计问题（改不动、越改越乱） | 阶段一重估 |
