# 阶段二 · 完整开发

**目标**：按确认后的计划完成本轮全部开发，并同步交付单元测试。
**入口**：G1 已确认。**出口**：人确认开发完成（G2）。

> 📌 本阶段**每一次回复**的末尾都要带阶段脚注（格式与措辞见 `SKILL.md` §0.1）。开发进行中通常是「继续本阶段 —— 已 x/N，无需你操作」。

> 📖 **开工前先读 `coding-conventions.md`**（与本文件同目录）：注释与文案用什么语言、emoji、界面文字的文风、改动边界在哪——别处没写的约定都在那里。

> AI 可以自主执行，但不能自主改变目标。

---

## 1. 「一次性」的确切含义

计划确认后，**一轮做完本轮计划内的全部改动**。

| 是 | 不是 |
|---|---|
| 改完计划列出的所有文件 | 拆成多轮「先做一半给你看看」 |
| 补全所有关联模块的适配 | 留下「关联模块下次再改」 |
| 同步写完单元测试 | 先写代码，「测试回头补」 |
| 自己先把能跑的部分跑通 | 交一堆半成品等人发现问题 |

**不留 TODO、不留「下次再」、不留注释掉的旧代码。**

**用户说「开始」之后不要停下来等回复。** 一路做到「可以请他拍板去阶段三」的程度——计划项全部完成、单测写完、自测通过——才停在 G2。途中的播报是让他随时能叫停，**不是请他逐项点头；播报完立刻做下一项**。会打断这条「一路做下去」的，一是人主动叫停，二是 §3 偏差分级里判定要停的偏差（**目标偏离**、**实现偏差**）——什么时候该停，以 §3 为唯一判据，不要在这里另立一份。

「一次性」不等于「不能中断」——环节6 的叫停权**永远有效**、随时可触发。

## 2. 同步编写单元测试（环节5）

测试不是验证「能不能跑」，而是**覆盖尽可能广、测试尽可能深**。必须覆盖 7 类维度：

| # | 维度 | 正例 | 反例 |
|---|---|---|---|
| 1 | **正常流程** | 输入合法数据 → 返回预期结果 | 只测了正常路径的中间状态，没测最终落库/渲染结果 |
| 2 | **异常流程** | 网络失败 → 返回明确的错误 + 不破坏既有状态 | `expect(() => fn()).not.toThrow()`——只证明不崩，没证明行为正确 |
| 3 | **边界条件** | 空数组 / 零 / 最大值 / 超长字符串 / 首次运行 | 只测 `[1,2,3]`，不测 `[]` 和 `[1]` |
| 4 | **极端输入** | 超大数据量 / 并发提交 / 非法字符 / SQL 与 HTML 注入串 | 只测「正常字符」，注入串没试过 |
| 5 | **核心业务逻辑** | 直接断言业务规则（折扣计算、状态流转、权限判定） | 只测了外层包装，核心分支没进 |
| 6 | **模块间交互** | A 调用 B 时，B 失败/超时/返回空时 A 的表现 | 模拟掉 B 后只测 A 的成功路径 |
| 7 | **回归风险点** | 本次改动**可能影响到的既有行为**，各补一条守卫测试 | 只测新功能，不管旧功能会不会被改坏 |

### 落点约定

- 测试文件遵循**本项目既有约定**（此处填：`<测试目录 / 命名规则 / 运行命令>`）。
- 新增测试与被测代码**同一次提交**，不分开。
- 每条测试的名字要说清「在什么情况下期望什么」，不要叫 `test1`。

## 3. 人工监督与纠偏（环节6）

人全程观察，持有**常驻叫停权**。发现偏离时执行四步协议：

```
1 立即叫停  →  2 指出偏差  →  3 纠正方向  →  4 继续执行
```

**你的义务**：听到叫停，**把手上的动作收在当前位置，不再往下扩展**——已经开始写的这一处可以写完（免得留半个坏文件），但**不新开文件、不新开计划项**。说一句你理解的偏差和纠正后的方向，然后继续。

### 偏差分级

**判据只有一条：人已拍板的「做什么」有没有变。** 与「文件在不在计划清单里」无关。

| 偏差类型 | 判据 | 例子 | 处理 |
|---|---|---|---|
| **目标偏离** | 改变了人已拍板的「做什么」 | 加了计划外的功能；换了技术方案；改了数据结构或对外行为 | **立即停**，报告 G1 重确认 |
| **计划补漏** | 计划自身漏项或矛盾，不补则跑不通；「做什么」没变 | 依赖表漏列（如 `tsconfig` 要 `@types/node` 但依赖表没写）；`npm install` 生成的 lock 文件；计划漏列的测试文件；让计划里的命令能跑通所需的最小改动 | **记录，继续执行**，在 G2 逐条列出 |
| **实现偏差** | 做法与计划描述不符但目标一致 | 换了等价写法、调整内部函数划分 | 停，说明差异，请人裁决 |
| **风格偏差** | 命名、代码组织、注释密度 | — | **记录，继续执行**，在 G2 一并报告 |

> ⚠️ **「改了计划外的文件」不必然是目标偏离。** 补漏也会改到计划外的文件。**分不清时按目标偏离处理——停下来问总是安全的。**

### 报告节奏

**每完成一个计划项就播报一行**并更新任务列表：

````
【阶段2：开发】已完成 3/7：数据结构定义、模块 A、模块 A 单测
下一项：模块 B

> **当前：阶段2 · 开发**
>
> **建议：继续本阶段** —— 还剩 4/7 项（模块 B、C、D 及其单测），无需你操作；发现问题随时叫停我。
````

不要闷头做完再一次性汇报——那等于放弃环节6。若一轮回复内确实来不及中途播报就做完了，**G2 报告必须逐项列出**完成情况，不能只写个总数——播报的目的是让人随时能叫停，G2 报告就是一轮做完时的那个出口。

🛑 **闸门 G2 — 开发完成移交**

停在何处：计划内全部改动完成、单测写完、自测通过。**此刻不得启动复核。**

本轮输出（≤10 行要点 + 逐条待确认项）：

```
计划项完成：7/7（逐条勾）
改动文件：<N 个，列关键几个>
计划外改动：<计划没写但实际新增/修改的文件，逐条标注属「计划补漏」还是「目标偏离」及原因；无则写「无」>
新增测试：<N 条，覆盖维度>
风格偏差记录：<执行阶段自主决定的事项，如有>
待确认项：
  1. <自测中发现但未处理的问题，如果有>
```
