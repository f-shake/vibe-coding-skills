# 阶段四 · 人工审查与系统验收

**目标**：回到人。既看代码对不对，更看**最终产品是不是对的**。
**入口**：G3 通过。**出口**：G4 + G5 都通过。

> 📌 本阶段**每一次回复**的末尾都要带阶段脚注（格式与措辞见 `SKILL.md` §0.1）。等审查/验收时是「继续本阶段 —— 等你操作完后回话」。

> 这一阶段 AI 不能自己签字。**任何自动化都替代不了人真正把系统跑起来。**

---

## 1. 人工代码审查（环节 ⑩）

| # | 审查点 |
|---|---|
| 1 | 有没有**改错地方** |
| 2 | 是否修改了**不应该修改**的代码 |
| 3 | 实现方式是否合理 |
| 4 | 是否符合**原来的开发计划**（阶段一那份） |
| 5 | 是否引入了**不必要的复杂度** |
| 6 | 是否存在潜在隐患 |

**不复核已被子代理覆盖的机械项**——错别字、未使用导入、格式，那些阶段三已经扫过了。

人这次要判断的是**一句话**：**AI 到底是不是按照我想要的方式，完成了这件事情？** 这是机器判断不了的：机器只能判断「代码自洽」，不能判断「这是不是我要的」。

### AI 的准备

- 提供**对照计划**的改动摘要（计划项 → 对应文件 → 状态）
- 提供 `git diff` 的阅读入口（或按模块分组的 diff）
- **主动标出**你在阶段二自主决定的事项（即当时记的风格偏差）
- 不要替人下结论说「代码没问题」

---

## 2. 人工系统验收（环节 ⑪）

把系统**真正运行起来**，从两个维度验收。

**维度 A · 前端体验**：页面是否正常渲染；界面是否符合预期；交互是否正常（点击、输入、切换、提交）；操作流程是否合理（符合直觉、没有多余步骤）；异常状态是否正确呈现（加载中 / 空 / 错误 / 无权限）。

**维度 B · 功能实现**：功能是否**真正实现**（不是「代码写了」，是「点下去有反应」）；核心流程是否正常；各模块之间是否正常协作；实际运行结果是否符合预期。

### 「真跑起来」的判定标准

AI 需要交付一份可执行的验收路径（**项目无关，此处填本项目实际的**）：

```
启动命令：<本项目此处填>
访问入口：<本项目此处填>
验收用例：
  1. <操作步骤> → <预期结果>
  2. <操作步骤> → <预期结果>
  3. <异常路径：故意触发失败> → <预期结果>
```

**必须包含至少一条异常路径用例**——只走正常路径的验收不算验收。

---

## 3. 问题回流规则

验收发现问题时，按问题性质决定回到哪个阶段：

| 问题性质 | 回流到 |
|---|---|
| **体验问题**（样式、文案、交互手感、加载态） | 阶段二 |
| **逻辑问题**（功能不对、数据错、顺序错） | 阶段三 |
| **需求级问题**（这不是我要的东西） | **阶段一** |

回流后必须重新走完后续闸门，**不得从中间插队**。
