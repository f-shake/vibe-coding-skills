# 阶段三 · 独立复核

**目标**：让一个**不知道前因后果**的 AI 挑战另一个 AI 的结果。
**入口**：闸门2 已确认。**出口**：复核收敛（闸门3）。

> 📌 本阶段**每一次回复**的末尾都要带阶段脚注（格式见 `SKILL.md` §0.1）。**一轮一停，永远不写「无需你操作」**——每轮结束时写「第 N 轮完成，等你示意」。
> 🚫 **本阶段不使用 goal 模式**（阶段二的 goal 已在闸门2 收口）——**一轮一停，复核一轮就停下报告**。见 §3 与 `goal-continuation.md` 开头「只用于阶段二」。
> 📌 **复核一轮就停下报告**（本阶段一轮一停，不用 goal 模式）——脚注相应写「第 N 轮完成，等你示意」。

**本阶段是 `vibe-coding` 的一环；复核循环本身怎么做（五问判断、收敛判据、轮次收窄、再复核机制、输入隔离纪律）由 `review-and-fix-cycle` 定义，此处不复述。** 读那份，别在这里找。

## 1. 为什么要独立子代理（环节7）

主代理写完代码后会带入**作者滤镜**：「我自己写的，所以肯定没问题」——这是最危险的自我确认偏差。

所以复核者必须**只看代码本身**：不知道主代理是怎么思考的，不知道之前的对话过程，不受主代理的结论或辩护影响。派发时**只喂事实，不喂理由**——喂了设计理由，子代理就开始替你的实现找补，复核就失效了。

## 2. 调用 `review-and-fix-cycle`（环节7~9）

```
调用（Skill 工具）：`review-and-fix-cycle`
  兜底（Skill 工具不可用时）：读技能目录下的 `review-and-fix-cycle/SKILL.md` 并照其执行
              其审查标准：`review-and-fix-cycle/references/code-review-guide.md`（A~H 八个分析角度）
  调用时机：闸门2 确认后
  传入：改动范围 / 文件清单 / 模式清单 / 基线引用 / 约定文件 `coding-conventions.md`（与本文件同目录）；以上**一律不含设计理由**
  期望产出：带文件路径与行号的问题清单 + 每条已确认/可能成立/已排除判定
  返回后：按该技能的第二阶段逐条判断、修复，再进入其三阶段的再复核循环
          （**修复后必须立刻送审**；最后一轮必须拿到子代理对最终版本的确认回执）
  轮次：逐轮收窄——第 1 轮全范围，之后只查上轮条目；正常 2 轮收敛，3 轮为上限
```

**子代理类型建议**：检查类任务用**只读子代理**（本平台有只读/搜索类就选它，没有就明确禁止它改文件）；修复由**主代理**执行，不交给子代理。

### 本阶段的编排职责

`review-and-fix-cycle` 管「怎么复核」，你在这里管「怎么把它接进流水线」：

- **改动范围取自阶段二的实际产出**，不是阶段一的计划。两者不一致时按 `phase-2-implementation.md` §3 的偏差分级处置（**判据完全一致，不要另立标准**）：补漏 → 以实际产出为准、差异记进闸门3 报告；目标偏离 → **必须停下来回闸门1**。
- **可以分批发货**：本轮改动含多个相对独立的模块时，每完成一组就复核一组，问题定位更准，不必攒到最后。
- **两类约定文件都要交**：**目标仓库自己的**（`CLAUDE.md` / `AGENTS.md` / `README.md`——角度 H 的判据，不交则约定类检查没有依据）与**本技能自带的** `coding-conventions.md`（与本文件同目录——它定义「什么算问题」，不交则复核者只能拿通用口味去判）。
- **循环发生在阶段三内部**：修复后重新送审不需重走闸门2。只有修复引入**计划外的功能**（目标偏离）才回闸门1。
- **轮次收窄与交付门槛**（最后一轮必须是子代理的**确认回执**而非主代理自述；交付版本须与子代理最后看过的那一份完全一致）见 `review-and-fix-cycle`。

## 3. 本阶段不使用 goal 模式

**阶段二的 goal 已在闸门2 收口。本阶段一轮一停**：复核一轮 → 停下报告 → 等你示意再进下一轮。理由见 [goal-continuation.md](goal-continuation.md)「只用于阶段二」。

**「一轮」的边界＝一次「送审 → 判断 → 再送审」的闭环**（收敛判据、轮次收窄、交付门槛由 `review-and-fix-cycle` 定义）。所以：

- **敲定一轮之前不要停下报告**——`review-and-fix-cycle` 要求「改完就送审，中间不插事」，向用户汇报不属于送审，不能插进来；
- **停点只有两个**：一轮闭环走完（停下报本轮结论等你示意），或撞上真该停下来问人的事（`goal-continuation.md` §6）；
- 只负责「轮与轮之间」的推进需要你示意，**轮次内部的送审/判断/修复不要你催**。

1. **驱动不会替你推进**——每轮复核结束就停。**想停随时能停**，代价只是下一轮要你说一声。
2. **本阶段有子代理当复核者**，而它调不了 `ask_user_question`——处置办法见 [goal-continuation.md](goal-continuation.md) §6 第二条（派发时就要求它把待裁决项写进最终报告）。

> ⚠️ **收敛上限一条都不放宽**：收敛判据、轮次收窄、**「连续 3 轮仍不收敛 → 升级人工」**（本文件 §4）——**不许试第四轮**。
> **轮次按扫描范围计，不按回合数、也不按派发次数**：第 1 轮全范围（**含分批发货——同一轮里派几批复核都算第 1 轮**），第 2 轮只覆盖上轮条目，第 3 轮只覆盖仍存在的项。每轮开头把轮次写进播报，到第 3 轮结束仍未收敛就**主动升级人工**。

## 4. 收敛与防死循环（环节9）

**收敛判据**、**轮次收窄规则**、**交付门槛**、**再复核机制**、**防死循环规则**均由 `review-and-fix-cycle` 定义。本阶段只额外强调一条：

> **连续 3 轮仍不收敛 → 停止推进，升级人工，重估方案。** 不要继续试——反复修不好通常意味着**方案本身有问题**（该回阶段一），而不是再多修两轮就能好。


未确认前禁止：
- 不得进入阶段四
- 不得跑任何最终验证（全量单测 / 端到端 / 发布测试）
