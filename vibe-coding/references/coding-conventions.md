# 编码与协作规范

从历史对话里沉淀出来的、**反复出现**的编码与协作规范。两条过滤：

- **只出现过一次的偶发要求，不收**（用户点名要收的除外，见 §4 最后两条）
- **别处已经写过的，不收**——`SKILL.md`、五个阶段文件、`review-and-fix-cycle` 里的（闸门、四禁令、只读子代理、复核纪律）一律不重复

**优先级**：本文件是补充。与 `SKILL.md` 或任一阶段文件的规则冲突时，**以阶段文件为准**。

落到具体仓库时，以该仓库自己的 `CLAUDE.md` / `AGENTS.md` / `README.md` 为准。

---

## 1. 事实与诚实

- 不确定、读不到、找不到，就照实说（“未找到”“未能确定”）。**严禁“大概是”“应该是”这类推测**，也不要编造。
- 结论必须落到**实际读取与工具输出**上：不凭印象填写，也不轻信他人的叙述——**包括用户自己的说法**（“重新读盘判断”）。
- **明确说出来，不要假装做了。**

## 2. 汇报

- **一律用中文。**
- **不要大段贴代码或贴原文，用你自己的话概括**（片段一般 ≤3 行）。
- **不要凑数报风格偏好**：“可以加注释”“命名不够好”这类改了也不影响行为的建议不提。**死代码、未用导入等清理项不在此列**——那是复核标准的正当产出（见 `review-and-fix-cycle`）。

## 3. 改动的边界

- **只做点名的定点改动**：不顺手改别的、不重写整段、不动其它文件，但觉得有必要可以提出来。
- 如果只是修改文档或代码的一部分（<50%），用 **Edit 局部修改**，不要 Write 整篇重写。

## 4. 语言与文案

- **注释与界面文案一律用中文。**
- 注释**解释“为什么”**，尤其是“为什么必须这样”的取舍，**不要复述代码**。
- **禁止在程序代码与显示标签里出现 emoji**，除非用户明确要求。（用户点名要收）
- **程序界面上的文字**：文风正式、语言精简；不要出现打断式的解释性插话；不要出现引号，必须出现时用 `“”`，不用 `「」`。（用户点名要收）

## 5. 并发与构建

- 可能**已有别的 agent 在跑**构建或测试，会抢 `obj/bin` 锁——不要凑上去跟着跑；真遇到文件占用错误，暂停提出来。
- **用户程序正在运行时不要构建**（会因文件锁失败）。
