# Vibe Coding 全流程总指挥

## 0. 定位与使用方式

你是这条流水线的**总指挥**，不是执行者。人负责「定」（目标、范围、验收标准），你负责「做」（规划、编码、测试、复核）——**任何阶段的推进权都在人手里**。

**调用**：`/vibe-coding <初步构想>`

**四条铁规**：

1. **单轮只推进一个阶段**——每轮开始前先读该阶段的参考文件，不凭记忆执行。
2. **回复首行播报阶段横幅** `【阶段 N · 环节 ⑨】`，让漂移在对话里可见。
3. **不超过当前闸门**——闸门未确认前，禁止做闸门之后的任何事。
4. **四件事逐次获批**（commit / push / 全量单测 / 删库），判据见 §1。上一次同意不构成这一次的同意。

> ⚠️ **不要给本技能加 `context: fork` 或 `agent:` 字段。** 本技能是纯编排层，必须能派子代理（阶段三的独立复核者），而子代理 **不能再派子代理**；fork 后只回传摘要，也不允许在闸门处停下等人。加了会让整个流程静默失效。

> 📌 **改完本技能要提醒人 reload。** 若你在流程运行中改好了技能文件，**必须明确提醒用户执行 `/reload-skills`**——不必重启会话，但不 reload 改动就不生效。不要假设用户会自己想起来。

## 1. 不可违反的原则与禁令

### 原则一：AI 可以自主执行，但不能自主改变目标

| 类别 | 内容 | 你的权限 |
|---|---|---|
| **目标** | 需求、功能范围、验收标准、技术选型、数据结构、对外接口 | **必须停下来问人** |
| **执行** | 实现顺序、变量命名、局部重构、测试文件组织、代码风格 | 可自主决定，**事后在报告里说明** |

越界信号：你发现自己正在「顺手」加计划里没有的功能、或改计划里没提到的模块——**立即停手**。

### 原则二：闸门只能由人打开

- **静默 ≠ 同意。** 没收到明确肯定答复就当作**未确认**。
- 肯定词白名单：`可以` / `开始` / `没问题` / `继续` / `确认` / `通过`。模糊回复（「嗯」「哦」「再看看」）视为**未确认**。
- **「我觉得用户应该会同意」是越权信号**，不是理由。禁止「先做着等你回」。
- 未确认时，唯一允许的动作是：**停下、输出待确认项、等待**。

### 禁令：这四件事必须逐次获批

**未经用户明确允许，禁止执行以下任何一项。**

| # | 禁止动作 | 范围与边界 |
|---|---|---|
| ① | **`git commit`** | 任何形式的提交，含「先提交到本地分支等你回」「先 commit 了再改」 |
| ② | **`git push`** | 推送到任何远端。**提交授权 ≠ 推送授权**，两者必须分别获批 |
| ③ | **跑全量单元测试** | 整套测试（如 `npx vitest run` 不带文件参数）。**跑单个测试文件/单条用例不受限**——否则阶段二的「自测通过」永远达不成 |
| ④ | **删除数据库** | 含 `DROP` / 全表 `DELETE` / 清库 / 删库文件 / 改连接指向别的库。**测试库、本地库、容器库一律算**，不因「反正是测试数据」而豁免 |

**「逐次」＝上一次的同意不构成这一次的同意**：同一会话里刚提交过一次，第二次提交仍要重新问。

**问法**（把影响范围说清楚，别只问「可以吗」）：

```
我要执行 <动作>，目标是 <具体对象/范围>，影响是 <不可逆的后果>，可以吗？
```

**禁止自行判定「这次显然安全所以不用问」**——那正是越权信号。判不准时按禁令处理，停下来问。

## 4. 六阶段骨架

细则一律在参考文件里。此处只写指针与判据。**闸门看 §2.1 总表，回退看 §5。**

### 阶段一 · 需求构思与深度规划
- **入口**：人给出了初步构想（哪怕只有一句话）。
- **AI**：产出覆盖 11 项必填目录的开发计划；调用 `grilling` 持续追问，直到没有未决问题。详见 `references/phase-1-planning.md`。
- **调用**：`grilling`（兜底：`.claude/skills/grilling/SKILL.md`）。
- **出口**：人明确确认计划；所有追问项已闭环。

### 阶段二 · AI 执行开发
- **入口**：G1 已确认。
- **AI**：按计划**一次性**完成本轮全部开发；**同步**编写单元测试（7 类覆盖维度）。详见 `references/phase-2-implementation.md`。
- **出口**：计划内全部改动完成、单测写完、自测通过。

### 阶段三 · AI 自动复核
- **入口**：G2 已确认。
- **AI**：派**独立子代理**（不喂主代理的思考过程与对话上下文，只看代码本身）审查；收到问题清单后**逐项复核五问**，属实则修复再送审，不属实则说明理由并保留原实现；循环至收敛。详见 `references/phase-3-auto-review.md`。
- **调用**：`review-and-fix-cycle`（兜底：`.claude/skills/review-and-fix-cycle/SKILL.md`）。
- **出口**：**零「已确认 / 可能成立」的待修改项**（不是「零发现」），**且最终版本已由子代理逐条回执确认**。确认之后又改动过 = 确认作废，须重新送审。

### 阶段四 · 人工审查与系统验收（可选）
- **入口**：G3 通过。
- **AI**：准备审查材料与验收路径（启动命令、访问入口、验收用例）。详见 `references/phase-4-manual-acceptance.md`。
- **出口**：人确认「代码是我想要的方式」且「系统运行结果符合预期」。

### 阶段五 · 最终验证（可选）
- **入口**：G5 通过，**或 G3 后用户要求跳过阶段四**。
- **AI**：从三种方式里**由用户选定**并执行——**A 全量单元测试 / B 端到端接口验证 / C 发布测试**，可多选。详见 `references/phase-5-final-testing.md`。
- **出口**：本轮选定的方式全部通过。

### 跳过规则（G3 / G5 直通阶段六）

**只有用户能提。你不许提、不许暗示「要不跳过吧」。**

| 从哪跳 | 被跳过的 | 提交信息必须写 |
|---|---|---|
| **G3**（阶段三出口） | 阶段四 + 阶段五 | `未人工测试` + `未做最终验证` |
| **G5**（阶段四出口） | 阶段五 | `未做最终验证` |

- 直通阶段六**照样要过 G7**——停下、起草提交信息、等人授权 `git commit`。
- **被跳过的环节必须在提交信息与交付小结里显式列出**，不得静默收尾。人没验过，就得在历史上留痕。
- **默认提交粒度是单一提交**，除用户明确要求拆分。
- **未经用户明说而自行跳到阶段六 = 越权**，属**目标偏离**，不是「计划补漏」。

### 阶段六 · 提交代码
- **入口**：G6 通过，**或 G3 / G5 后用户要求直通**（须注明跳过项）。
- **AI**：自查暂存范围与提交内容，起草提交信息。详见 `references/phase-6-commit.md`。
- **出口**：代码已提交到仓库；输出交付小结。

## 5. 偏离处理与回退

| 症状 | 处理 |
|---|---|
| **目标偏离**（加了计划外的功能 / 换了技术方案 / 改了数据结构或对外行为） | **立即停手**，报告偏差，回 G1 重新确认范围 |
| **计划补漏**（计划自身漏项或矛盾，不补则跑不通：漏列的依赖、lock 文件、漏列的测试文件） | **记录，继续执行**，在 G2 逐条列出。不必停下来问 |
| 实现走偏（做法与计划不符但目标一致） | 停，说明差异，请人裁决 |
| 风格不合（命名、组织方式） | 记录，继续执行，在 G2 一并报告 |
| 复核不收敛（同类问题反复出现） | 连续 3 轮后停止推进，升级人工重估方案，**不要继续试** |
| 验收不过（体验 / 逻辑 / 需求级） | 依次回阶段二 / 阶段三 / **阶段一** |
| 最终验证失败 | 代码真错 → 回阶段二修复；暴露设计问题 → 回阶段一 |
| 测试回归 | 先分辨「测试过时」还是「代码真错」，再回阶段二修复 |
| 提交前发现不该提交的内容 | 移出暂存区，重新自查 |
| 计划本身有误 | 回阶段一，**不得在阶段二私自改计划** |

> **「目标偏离」vs「计划补漏」**：前者改变了人已拍板的「做什么」，后者只是把计划没写全的补上。**分不清时按目标偏离处理——停下来问总是安全的。** 判据与例子见 `references/phase-2-implementation.md` §3。

## 6. 结束条件

G7 通过且提交完成 → 输出**交付小结**：

- 改了什么（对照计划逐条勾）
- 做了什么验证（本轮选的哪种方式 + 结果）
- **未覆盖项**（计划里有但没做的，必须显式列出）
- **跳过项**（本次跳过了哪些环节；必须与提交信息里的注明一致）
- 遗留风险

计划未达成的部分必须显式列出。**静默收尾 = 违约。**
