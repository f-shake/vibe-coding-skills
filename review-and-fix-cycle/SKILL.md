# 复核-修复-再复核工作流

## 概要

适用于**批量自动化修改后确保正确性**的场景。核心流程：

```
独立子代理（复核） → 主代理（逐条判断 + 修复） → 同一子代理（再复核）
```

**最后一环必须是子代理的确认回执，不能是主代理的自述。** 交付的版本 = 子代理最后看过的那一份。

### 送审前置：窄范围单测必须先绿

**每次把代码交给子代理复核前，先跑通本次改动涉及的那部分单元测试**（窄范围，不是全量）。

带红的代码送审＝让复核者在必现的编译错/断言错上烧掉一整轮，还会把「本来就坏的」误报成新发现，污染问题清单。**自己先跑一遍能跑绿的，再交出去。**

> 窄范围单测不受禁令限制（禁令只针对**全量** 测试套件）。跑单文件/单用例随时可以。

---

## 适用场景

任何有一定规模的代码修改都可以使用。典型例子：**批量替换**（硬编码值、API 重命名、import 路径迁移）、**代码重构**（CSS 合并、组件拆分、函数提取、类型改造）、**跨文件迁移**（移动文件、拆分模块、切换依赖库）、**架构调整**（接口抽象、层间解耦、设计模式引入）、**自动化修复**（Lint 自动修复后的正确性确认）。

核心判断标准：**修改涉及多个文件，且你无法逐行审查每一处改动**时，就该走这个流程。

---

## 流程

### 第一阶段：独立子代理复核（发现问题）

**角色**：`Explore` 类型子代理（只读，不会意外改文件）。**修复由主代理执行，不交给子代理。**
**任务**：对已修改的内容全面检查，输出问题清单

**审查标准**：子代理必须遵循 `.claude/skills/review-and-fix-cycle/references/code-review-guide.md`。该指南按 A~H 八个分析角度检查，按已确认 / 可能成立 / 已排除判定，保留前两者、丢弃已排除。**先把该文件整个交给子代理，不要在派发提示里转述其内容**——转述会丢细节，也会随本文件改动而漂移。

**输入隔离纪律**（决定复核是否有效）：

```
✅ 给：改动范围、文件清单、diff、基线引用、项目约定文件路径
❌ 不给：「我这样做是因为……」「这个设计是故意的」「应该没问题」
❌ 不给：主代理的思路总结、之前的评审结论
```

复核者的价值正来自于**不知道你的思路**。一旦喂了设计理由，它就开始替你的实现找补。

**输出格式**：

```
## 问题 N：问题简述
- **文件**：路径
- **行号**：N
- **严重性**：错误 / 警告 / 清理
- **说明**：具体是什么问题
```

**要点**：指定具体的检查范围（文件列表、模式列表）；要求提供**精确的文件路径和行号**——没有行号的问题无法快速判断属实性。

### 第二阶段：主代理逐条判断（决定修复）

**角色**：当前对话中的主代理（你）
**任务**：对子代理的每条发现逐一判断

| 判断 | 含义 | 后续操作 |
|------|------|---------|
| ✅ **属实** | 问题真实存在，且值得修复 | 执行修复 |
| ❌ **不属实** | 子代理误判、或已有意为之的设计决策 | **写明理由**，保留原实现 |
| ⚠️ **部分属实** | 问题存在但有额外上下文 | 按实际情况处理 |

**要点**：
- 逐条回应，不要笼统接受或拒绝
- 对每条判断给出简短理由；**判定「不属实」却不写理由 = 静默丢弃**，不允许
- 判断前可自行 grep/read 验证（不轻信子代理的结论）
- **判断优先于修复**：先对所有问题做判断，再批量修复，不要在判断过程中穿插修复

### 第三阶段：子代理再复核（确认修复）

**角色**：**同一**子代理（通过 `SendMessage` 恢复其上下文）
**任务**：检查第二阶段修复的结果是否正确

```javascript
SendMessage({
  to: "子代理的ID",
  summary: "复核上一轮的 N 个问题",
  message: `【已修复】逐条确认是否真的修好，回「已修复」/「仍存在」：
1. ...
2. ...
【判定不属实】以下是主代理的驳回理由，请表态「接受」（理由成立）/「驳回」（仍坚持是问题）：
1. <问题> — 理由：...
只回答以上条目，不要扫描新文件。`
})
```

**要点**：
- 通过 `SendMessage` 恢复**同一子代理**——它保留之前检查时的上下文，无需重新扫描
- **修复完成的下一步动作只能是 `SendMessage`。** 不要先写文档、先向用户汇报「已完成」、先进入下一阶段——**改完就送审，中间不插事**
- **送审内容要带上「不属实」的理由。** 子代理得看到你的理由才可能表态接受或坚持；只报「已修复的」而不交「被驳回的」，等于自己给自己放行

> ⚠️ **这是整条流程最常被跳过的一步。** 主代理修完一轮后倾向自述「已修复」就往下走。**主代理的自述不算确认**——没有子代理的回执，这一轮就没有结束。

### 循环至收敛

```
审查 → 判断 → 修复 → 再审查 → ...
```

**收敛判据**：不是「零发现」，而是 **零「已确认 / 可能成立」的待修改项**。子代理仍可报出问题，只要每条都被判定为已排除或「不属实」并留有理由，即算收敛。要求「零发现」会逼着模型制造无意义的改动来讨好复核者。

**但「不属实」必须被子代理 `接受` 才算闭环**——主代理单方面驳回不算；仍处 `仍存在` 或 `驳回` 的条目就是待修改项。

**最后一轮必须是「确认」，不是「发现」。** 收敛的形态是：子代理对**最终版本**逐条回执 `已修复` 或 `接受`，无 `仍存在` / `驳回`。**以一团新发现收尾 = 没收敛。**

#### 轮次收窄（轮数不宜多）

| 轮次 | 覆盖范围 | 典型产出 |
|---|---|---|
| 第 1 轮 | **全范围**：本次改动涉及的所有文件 | 问题清单 |
| 第 2 轮 | **只覆盖上一轮的条目**，不再扫描新文件：<br>· 判定属实并已修复 → 复查是否**真的**修好<br>· 判定不属实 → **把主代理的理由交给子代理**，要它表态接受还是仍坚持 | 逐条回执 `已修复` / `仍存在` / `接受` / `驳回` |
| 第 3 轮 | 只覆盖第 2 轮仍 `仍存在` 或 `驳回` 的条目 | 最后一次回执 |

> **收窄的是「代码扫描范围」，不是「把关强度」。** 第 2 轮不再满仓库找新问题，但上一轮的**每一条结论都必须过子代理的手**——尤其「不属实」的那些。主代理自己判「不属实」之后就再没人管，等于把独立复核阉掉。

- **`驳回` ＝未闭环。** 子代理不接受「不属实」的理由 → 该条回炉：主代理要么改判属实并修复，要么补齐站得住脚的理由再送审。
- **收窄判据**：每轮发现数应**严格递减**。若第 N+1 轮 ≥ 第 N 轮 → **不等满 3 轮就停止并升级人工**（这是「方案本身有问题」的信号，不是「再多修两轮就好」）。
- **范围外的发现照报不误**，不许因为「不在本轮范围」就压下去——但**计入「轮次外发现」，不据此扩大本轮范围**。若轮次外发现 ≥ 2 条，说明第 1 轮范围划窄了：**重开一轮全范围**，而不是继续收窄。
- **正常收敛是 2 轮**（第 1 轮发现 → 第 2 轮确认）。出现第 3 轮，说明第 1 轮的修复质量有问题。

#### 交付门槛：确认记录绑定内容

- 收敛后向用户或下游阶段交付时，**必须附「子代理确认记录」**：轮次、覆盖范围、逐条回执。**主代理自述「已确认」无效。**
- **确认记录绑定到具体内容。** 最后一轮确认之后，该版本**只要又被改动过一个字符**（补个注释、改个笔误都算），**记录立即作废**，必须重新送审确认后才算完成。
- 交付前先自问：**「我现在交付的内容，和子代理最后看过的内容，是同一份吗？」** 答「否」或答不上来 → 回第三阶段。

**防死循环**：连续 3 轮仍不收敛（同类问题反复出现 / 修一个冒两个）→ **停止推进**，升级人工，重估方案。不要继续试。

## 示例

以一次 CSS 合并为例：

**第一阶段输出**

```
问题 1：config-styles.css 是死代码（无 import 引用）
- 文件：frontend/src/components/config/config-styles.css
- 严重性：清理
- 说明：整个文件不再被任何组件导入

问题 2：ConfigPage.vue 第 153 行 font-family 硬编码
- 文件：frontend/src/components/config/ConfigPage.vue
- 行号：153
- 严重性：清理
```

**第二阶段判断**

| 问题 | 判断 | 理由 |
|------|------|------|
| 问题 1 | ✅ 属实 | grep 确认无任何 import，直接删除 |
| 问题 2 | ✅ 属实 | 应替换为 `var(--font-mono)` |
| 问题 3 | ❌ 不属实 | 该文件中的 #f56c6c 是调色板颜色，非错误语义，不应替换 |

**第三阶段确认**

```
问题 1：已修复 — 文件已删除
问题 2：已修复 — 已替换为 var(--font-mono)
问题 3：接受 — 收到主代理的驳回理由（调色板颜色，非错误语义），理由成立，撤回该发现
```

注意第 3 条：第 2 轮不扫描新文件，只对着第 1 轮的条目做结论复核——这就是轮次收窄。
